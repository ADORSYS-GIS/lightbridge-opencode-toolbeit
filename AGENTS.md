# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, Cursor, Codex, Cline, …) when working with code in this repository. It mirrors [`CLAUDE.md`](CLAUDE.md) — keep the two in sync; when you edit one, copy the change across in the same PR.

## What this repo is

A **pnpm workspace** of OpenCode plugins under the `@vymalo` npm scope. There are **eight** runtime plugins plus a Rolldown-based bundler — all plugins target the **OpenCode v2 plugin API** (`@opencode/plugin`, authored on its Effect surface `@opencode/plugin/effect` — [ADR-0019](docs/adr/0019-opencode-v2-cutover.md); the migration from v1 is complete and there is no dual-support build) and ship to npm independently — plus **two** published **MCP servers** (one exposing the browser tools, one exposing the devtools utilities) for any MCP client, and one private **browser extension** app under `apps/` (the companion to the browser plugin/MCP server). Three more published packages are shared libraries other packages build on rather than plugins in their own right: `@vymalo/opencode-auth-core` (OAuth / RFC 8693 token-exchange primitives — `TokenRuntime`, used by oauth2 and repo-auth), `@vymalo/opencode-core-otel` (the OTel engine — exporters, recorder, resource, the `TokenSource` seam, and the shared process-exit drain `registerExitHandlers`, which re-raises SIGINT/SIGTERM so a bare signal listener cannot keep the host alive — [ADR-0018](docs/adr/0018-exit-handlers-reraise-the-signal.md) — used by otel and lightbridge), and `@vymalo/opencode-provider-sync` (the provider-registration + OAuth-backed model-sync engine — `ProviderModelSyncEngine`, cache, scheduler, host-config wiring helpers — extracted from oauth2 per [ADR-0016](docs/adr/0016-provider-sync-extraction.md); composed by both oauth2 and, since [ADR-0017](docs/adr/0017-lightbridge-all-in-one.md), lightbridge's optional `register` module). In total there are **sixteen** workspace packages: the **thirteen** published ones and **three** private ones (the workspace root, `@vymalo/opencode-oauth2-bundle`, and `@vymalo/opencode-browser-extension`).

The plugins are deliberately decoupled: `opencode-models-info`, `opencode-ratelimit`, `opencode-repo-auth`, and `opencode-browser` do not import from `opencode-oauth2` (or each other) and work with any auth scheme (static API key, oauth2, none) because each only touches the v2 domain it registers against (provider, model, tool, session, …) — there is no shared config object any more (browser additionally hosts its own bridge). **Ordering.** Within a domain, transforms run in registration order and a later plugin's transform sees an earlier one's changes (documented in [`docs/models-info.md`](docs/models-info.md#the-cross-plugin-handoff-contract-v2) and [`docs/provider-sync.md`](docs/provider-sync.md)), so for a fully-v2 suite the rule is simply **list `@vymalo/opencode-oauth2` first**:

- **oauth2 before models-info** — models-info inherits the bearer oauth2 stamps on `Provider.Info.headers` (see the composition contract below). Wrong order shows up as `models_info_fetch_failed_no_cache` (HTTP 401).
- **oauth2 before lightbridge** — lightbridge's `register` module detects "this provider is already managed by oauth2" by reading the `settings.oauth2` / `settings.oauth2ModelSync` marker oauth2 puts on every provider it manages (`markManaged`, `packages/opencode-oauth2/src/opencode.ts:71`, applied at `:267`; read by `hasOAuth2Conflict`, `packages/opencode-lightbridge/src/config.ts:269`, called at `packages/opencode-lightbridge/src/opencode.ts:511`). A plugin cannot see another plugin's `ctx.options`, so the marker is the only signal, and oauth2 stamps it inside its own `provider.transform`. **The order is a requirement, not a preference.** Listed first, lightbridge never touches an oauth2-managed `auth.id`. Listed after, its first pass cannot see the marker, so it builds its `ProviderModelSyncEngine` and runs a warmup sync against the same shared token cache oauth2 uses; it stands the engine down (`engine.stop()`) only once a later pass (oauth2's own `provider.reload()`) shows the marker. The scheduler-ownership guard inside `ProviderModelSyncEngine` keeps two engines from polling that cache concurrently, but the wasted warmup and the extra log noise are the price of the wrong order. See [`docs/lightbridge.md`](docs/lightbridge.md).
- **oauth2 before repo-auth** — also a requirement, for the same reason: repo-auth's double-management guard (`hasOAuth2Conflict`, `packages/opencode-repo-auth/src/config.ts:200`) reads that marker (or an `integrationID`). Listed first, repo-auth skips oauth2's providers from its first pass. Listed after, its first pass can still claim a provider oauth2 manages (warmup and stamping included) until oauth2's `provider.reload()` shows the marker and the next pass drops it. Never enable both on one provider.
- `ratelimit`, `browser`, `devtools` and `otel` have **no ordering requirement**: they touch neither auth nor the provider definition (ratelimit and otel register against `session.hook`s that coexist regardless of order).

So a typical stack is `oauth2 → (repo-auth \| lightbridge) → models-info → ratelimit`, with the rest anywhere.

## Common commands

```sh
pnpm install                 # bootstrap workspace
pnpm -r build                # compile all packages (oxc → dist/; emit only, no type check)
pnpm -r typecheck            # tsc --noEmit across packages
pnpm -r test                 # vitest run in each package that has tests (fast, no coverage)
pnpm coverage                # vitest run --coverage per package; FAILS below per-package thresholds
pnpm lint                    # biome lint (full repo)
pnpm format                  # biome format --write
pnpm format:check            # biome format (no write) — part of the pre-push gate
```

Pre-push gate (run all five before opening a PR): `pnpm -r build && pnpm -r typecheck && pnpm coverage && pnpm lint && pnpm format:check`. (`pnpm coverage` runs the tests **and** enforces coverage; CI runs the same. Use the faster `pnpm -r test` for local iteration.)

Coverage thresholds are per-package, declared in each `vitest.config.ts` (`test.coverage.thresholds`), set a few points below current so a regression fails CI without exact-match churn. `@vymalo/opencode-browser` is the bar (~88%+); `opencode-browser-mcp` excludes its stdio `bin` (`mcp.ts`) from the metric (it's e2e-only); the **browser extension floor is intentionally low** (chrome/DOM/React glue is verified manually — raise it once a fake-browser harness lands).

Per-package iteration (much faster):

```sh
pnpm --filter @vymalo/opencode-oauth2 test
pnpm --filter @vymalo/opencode-oauth2 build
pnpm --filter @vymalo/opencode-models-info typecheck
```

Single-test run inside a package:

```sh
pnpm --filter @vymalo/opencode-oauth2 exec vitest run path/to/file.test.ts
pnpm --filter @vymalo/opencode-oauth2 exec vitest run -t "ensureAccessToken"   # by test name
```

Watch mode: `pnpm --filter <pkg> exec vitest` (no `run`).

### Integration tests (Docker)

A reusable compose stack of HTTP backends lives under [`test-env/`](test-env/). Currently a WireMock service stubs the OpenRouter-shaped `/v1/models` endpoint for `@vymalo/opencode-models-info` and a Keycloak-shaped RFC 8693 token-exchange endpoint for `@vymalo/opencode-repo-auth`; a Keycloak service is sketched-in (commented out) for the upcoming `@vymalo/opencode-oauth2` integration suite.

```sh
pnpm test:env:up               # docker compose up (waits for healthcheck)
pnpm --filter @vymalo/opencode-models-info test:integration
pnpm --filter @vymalo/opencode-repo-auth test:integration
pnpm test:env:down             # docker compose down -v
# or one-shot:
pnpm test:integration          # compose up → all packages' integration suites → compose down
```

Integration tests live under `test/integration/**/*.test.ts`, run via a separate `vitest.integration.config.ts`, and **skip themselves** when their `INTEGRATION_*` env var is unset (`INTEGRATION_MODELS_INFO_URL`, `INTEGRATION_REPO_AUTH_TOKEN_URL`) — so the default `pnpm test` stays hermetic. Stubs are at [`test-env/wiremock/mappings/`](test-env/wiremock/mappings/) and [`test-env/wiremock/__files/`](test-env/wiremock/__files/); editing them needs either a `wiremock` container restart or `curl -X POST http://127.0.0.1:18080/__admin/mappings/reset`.

## Architecture: how the plugins fit OpenCode

A v2 plugin is `Plugin.define({ id, effect })` over `@opencode/plugin/effect` ([ADR-0019](docs/adr/0019-opencode-v2-cutover.md)). The Effect body receives a `ctx` and registers changes with the **domain** that owns them; v2 has no mutable global config object and nothing is returned. The registrations this repo uses:

- **`ctx.provider.transform(editor => …)`** — the provider domain. oauth2 registers managed providers, merges discovered models and stamps the cached bearer; repo-auth opts providers in and stamps the project bearer; lightbridge's `register` module does oauth2's job for its one `auth.id`; ratelimit reads its opt-in set and models-info records provider headers (both read-only). Transform callbacks must stay **synchronous and cheap**: async work (token refresh, model sync) runs in a background queue and calls `ctx.provider.reload()` when it has something new.
- **`ctx.model.transform(editor => …)`** — the model domain (models-info enrichment; `ctx.model.reload()` re-runs it).
- **`ctx.tool.transform(editor => editor.add(…))`** — tool registration with raw JSON-Schema input (browser, devtools).
- **`ctx.session.hook(name, handler)`** — per-request and per-turn seams: `"model.request"` (oauth2, repo-auth and lightbridge's gateway inject `Authorization` into `event.headers`; otel writes `traceparent`), `"http.request"` / `"http.response"` / `"retry"` (ratelimit; oauth2's Responses-SSE repair; lightbridge's trace context), `"prompt"` / `"context"` (otel).
- **`ctx.tool.hook("execute.before" | "execute.after")`, `ctx.permission.hook("evaluate")`, `ctx.event.subscribe({ types })`** — the observer surface (otel, lightbridge's `otel` module).
- **Configuration.** Plugin options arrive as `ctx.options` (the `plugins` entry `{ package, options }`); per-provider opt-ins are keys on the provider's `settings` (`settings.rateLimit`, `settings.modelsInfoUrl`, `settings.repoAuth`, `settings.oauth2`, …). `Provider.Settings` is an open struct, and `Provider.Info` has no `options` or `fetch` field.

The whole picture sits in [`docs/architecture.md`](docs/architecture.md). If you're modifying hook behavior, read it first — it documents token lifecycle per flow, cache layout, the TTY-aware warmup logic, and which events you should expect in the log stream.

### Distribution via `.well-known/opencode`

The primary way these plugins reach users: a server publishes a `.well-known/opencode` document (`{ auth?, config?, remote_config? }` — a command-based `auth` block plus a `config` block listing `plugins` + `providers`; on v2 the origin becomes an Integration, see [ADR-0020](docs/adr/0020-oauth2-integration-domain.md)), and `opencode auth login <url>` adopts it — no local `opencode.json` needed. OpenCode re-fetches and merges that `config` on every launch, so the provider definition is **not** stored on the client (only a `wellknown` pointer lands in `auth.json`; the real OAuth token lives in the oauth2 plugin's own cache). When debugging "where is this provider configured?", the answer is usually "served from the well-known URL, fetched fresh each boot." Full mechanics + gotchas in [`docs/well-known.md`](docs/well-known.md).

### Per-package file layout convention

All plugins follow the same shape:

```
packages/<plugin>/
├── src/
│   ├── index.ts        # OpenCode entry — re-exports default plugin
│   ├── opencode.ts     # Plugin factory: createXxxPlugin(opts) → Plugin
│   ├── lib.ts          # Public library API (exposed via "./lib" subpath in exports)
│   ├── plugin.ts       # Core runtime logic (split from opencode.ts so it stays testable)
│   ├── cache.ts        # FileCacheStore — per-OS cache dir, atomic rename, 0o600
│   ├── logging.ts      # Effect logger adapter (captureHostContext, createEffectLogger), resolveLogLevel, secret redaction
│   └── …
└── test/               # vitest, *.test.ts
```

`opencode-ratelimit` follows the same shape **minus `cache.ts`** (its rate-limit state is in-memory only — a reset window is seconds, so persisting it would only serve stale data) and **plus `headers.ts`** (a pure parser for the `x-ratelimit-*` triple). It was the first package ported to v2, and its `opencode.ts` and `logging.ts` are the template the other packages copied: `opencode.ts` is a `Plugin.define({ id, effect })` over `@opencode/plugin/effect`, and `logging.ts` holds `captureHostContext` + `createEffectLogger` — the Effect-logger adapter every package now carries. Its engine (`plugin.ts`, `config.ts`, `headers.ts`) is plain TS and never imports the plugin API, which is what made the port cheap.

`opencode-repo-auth` follows the same shape **minus `cache.ts`** (token persistence is auth-core's `FileCacheStore` reached through `TokenRuntime`; the plugin keeps only in-memory runtime state) and **plus `git.ts`** (worktree-aware, off-disk `.git/config` origin-remote resolution + `normalizeRemote` — log-only). Built on `@vymalo/opencode-auth-core`: one `TokenRuntime` keyed by the **human** identity, exchanging via the generic `exchangeTo(key, subjectToken, extraParams)` extension added for the `project_id` flow (see [the auth-core gap](docs/repo-auth.md#the-auth-core-gap-key-decision)). Alongside oauth2 and lightbridge's `gateway` module, one of three that inject `Authorization` headers (`session.hook("model.request")`), on **managed providers only**, injecting nothing on exchange errors.

`opencode-browser` follows the same shape **minus `cache.ts`** (broker state is in-memory) and **plus**: `protocol.ts` (the dependency-free wire-frame contract, mirrored into the extension), `transport.ts` (the `BridgeTransport` seam + `isAddrInUse`) and `node-transport.ts` (the `ws`-backed host transport + guest socket, runs under Bun *and* Node — shared with the MCP server via `./lib`; async `listen` for bind-based election), `broker.ts` (role-aware broker: executors + agents + group-ownership routing, DI-tested), `agent-client.ts` (guest-agent WS client), `endpoint.ts` (try-bind → host-or-guest auto-election with failover), `token-file.ts` (shared `bridge.json`), `catalog.ts` + `schema.ts` (the neutral tool surface), and `tools.ts` (the `ctx.tool.transform` adapter over the catalog). It is the only plugin that **hosts a server** (devtools also registers tools, but has no bridge). The companion extension under `apps/browser-extension` is a WXT project (not the per-package `src/` layout) — its engine lives in `src/background/` (bridge client, command router, group registry, CDP + content executors, `page-actions` injected via `browser.scripting.executeScript`, `feedback`/`feedback-overlay`/`feedback-side-panel` for the `interactive` HITL flow) and its UI in `src/entrypoints/{popup,options,sidepanel}` over Dexie (the `sidepanel` is the docked annotation fallback for overlay-blocked pages). Promise-awaited extension API calls go through `browser` from `wxt/browser`, never `chrome.*` — Firefox's `chrome.*` is callback-only, so awaiting it resolves to `undefined` there (issue #63); `chrome.*` remains only for event registration, synchronous calls, feature detection, `cdp.ts`'s callback-style debugger calls, and the serialized functions injected into pages. `apps/browser-extension/test/promise-namespace-guard.test.ts` enforces the awaited/chained half of that rule.

**Important — two entry points per published package:**

- `"."` resolves to `dist/index.js` and is what OpenCode discovers. The host iterates every named export and rejects anything that isn't a `Plugin` function, so `index.ts` is kept *intentionally tiny* (a single `export { default } from "./opencode.js";`). See [`packages/opencode-oauth2/src/index.ts`](packages/opencode-oauth2/src/index.ts) and the matching `slim main entry` fix in commit history.
- `"./lib"` resolves to `dist/lib.js` and is the library API for embedders. New utility exports go through `lib.ts`, not `index.ts`.

### Composition contract (models-info)

`@vymalo/opencode-models-info` enriches models through `ctx.model.transform`, over whatever providers and models the provider domain has already produced. It opts in per provider via `settings.modelsInfoUrl` (keys are flat on `settings`, no `meta` wrapper) and the merge is **upstream-wins**: a field already present on a model entry is never overwritten. This is deliberate — it means the plugin is safe to enable globally and lets handwritten config take precedence. The escape hatch is `settings.modelsInfoOverwrite` (array of mapped field names) — fields listed there are exempt from upstream-wins so the endpoint value can replace one another plugin auto-stamped. The motivating case: oauth2's discovery writes a *normalized* `name` (`kimi-k2.6` → `Kimi K2.6`) onto every model, which upstream-wins then freezes; `"modelsInfoOverwrite": ["name"]` lets the endpoint's real name win. (`modalities`/`attachment` are *not* pre-stamped by oauth2, so vision support enriches without an override — if it's missing, suspect a stale cache or failed fetch, not the merge.) `settings.modelsInfoHideTextOnly` is the membership-side counterpart: instead of overwriting a field, it *removes* a model from the provider's model list outright — when the catalog reports it text-only, or when the catalog has no entry for it at all — making `modelsInfoUrl` authoritative for which models exist even over oauth2's own `/v1/models` discovery. Off by default; see [`docs/models-info.md`](docs/models-info.md#hiding-text-only-models--catalog-authoritative-membership).

**The one cross-plugin coupling.** Despite being decoupled at the import level, the two plugins meet in the provider record — and on v2 the mechanism changed. v1 had one shared mutable object (oauth2 wrote `provider.options.headers.Authorization` in its `config` hook, models-info forwarded `options.headers`); v2 has neither `options` nor a shared object, so the handoff is now **`Provider.Info.headers.Authorization`**, written by oauth2 inside its `ctx.provider.transform` and read by models-info when it fetches `modelsInfoUrl`. It is split in two halves because transform callbacks must be synchronous:

- *Async half (owner):* `resolveCachedBearer` (`packages/opencode-provider-sync/src/opencode-helpers.ts:625`) does a refresh-only ensure (`ensureAccessToken(id, { interactive: false })`, so a near-expiry token is refreshed rather than skipped and no second login prompt opens). oauth2 runs it per server in its background build (`packages/opencode-oauth2/src/opencode.ts:202`), caches the result, then calls `ctx.provider.reload()` (`:212`) so the transform re-runs.
- *Sync half (owner):* `propagateCachedBearer` (`opencode-helpers.ts:668`, called from oauth2's provider transform at `packages/opencode-oauth2/src/opencode.ts:277`) stamps the cached `"<tokenType> <accessToken>"` onto the provider's `headers`; a user-set `Authorization` (case-insensitive) is never overwritten.
- *Consumer:* models-info reads the provider's headers through `editor.provider.list()` in its model transform (`packages/opencode-models-info/src/plugin.ts:250`, resolved at `:159`). Because it is **not documented** whether `ModelEditor.provider` reflects provider-domain transform output, it also registers a read-only `ctx.provider.transform` (`packages/opencode-models-info/src/opencode.ts:99`) that remembers the headers, and falls back to those (`models_info_provider_headers_resolved` reports `source: model-domain | provider-domain | none`). A load that failed with no cache (typically HTTP 401 before the bearer landed) is retried exactly once per distinct header set (`plugin.ts:224`), never in a loop.

`session.hook("model.request")` re-injects a fresh token on every inference request, so a stale stamped header can only ever affect the metadata fetch, never inference. **The ordering requirement is unchanged: `@vymalo/opencode-oauth2` must be listed before `@vymalo/opencode-models-info`** (the provider-domain transform has to have stamped the bearer before models-info observes it). Symptom of getting this wrong: `models_info_fetch_failed_no_cache` (HTTP 401). Owner-side spec: [`docs/provider-sync.md`](docs/provider-sync.md#the-authorization-handoff-to-models-info-v2-contract).

When changing the mapping in [`packages/opencode-models-info/src/mapping.ts`](packages/opencode-models-info/src/mapping.ts):

- OpenRouter's `pricing.prompt` / `.completion` are USD-per-token strings; OpenCode's `cost.input` / `cost.output` are USD-per-1M-tokens numbers. The conversion (`* 1_000_000` then round to 6 decimals) lives in `mapping.ts`. Don't move it.
- `limit` only emits if **both** `context` (`top_provider.context_length ?? context_length`) and `output` (`top_provider.max_completion_tokens`) are known — partial `limit` blocks are invalid in OpenCode's schema. Consequence worth knowing: if the source endpoint omits these, OpenCode backfills the runtime model's required `limit` to `{0,0}` and its UI treats the model as incomplete, hiding `cost` too even though it enriched fine. This is a *source-data* gap, not a plugin bug — see [`docs/troubleshooting.md`](docs/troubleshooting.md).
- Modalities are filtered to OpenCode's enum (`text | audio | image | video | pdf`) — `"file"` and other OpenRouter values are dropped.
- `tool_call` / `reasoning` / `temperature` are derived from the entry's `supported_parameters` array (`tools`/`tool_choice` → `tool_call`; `reasoning`/`reasoning_effort`/`thinking` → `reasoning`). The mapper only ever sets these to `true`; a capability the UI shows as disabled usually means the field is absent from the endpoint payload.

## Conventions worth knowing

- **Biome, not ESLint/Prettier.** Config in [`biome.json`](biome.json) — double quotes, 100-col, no trailing commas, semicolons always. `noNonNullAssertion` is a warning the existing code stays clean of; mirror that in new code (`@vymalo/opencode-oauth2` has 0 warnings, treat that as the bar).
- **Strict TS.** Base config is in [`tsconfig.base.json`](tsconfig.base.json) — `ES2022` + `NodeNext` + `strict: true` + `isolatedDeclarations: true`. That last one is load-bearing: `build` emits with **oxc** and never type-checks, so every export needs a type the compiler can read off a single file. `typecheck` (`tsc --noEmit`) is the only type-safety gate — a green `build` means nothing about types. See [ADR-0010](docs/adr/0010-oxc-build-isolated-declarations.md). Per-package tsconfig only sets `rootDir`/`outDir`. `lib.ts` re-exports are the public surface.
- **Vitest** is the test runner; each package owns a `vitest.config.ts` (with a `coverage` block + per-package thresholds enforced by `pnpm coverage`). Tests live in `test/`, not co-located. Coverage uses the v8 provider (`@vitest/coverage-v8`).
- **Node ≥ 22** for the runtime packages (set in each package.json `engines`). Use `node:` prefixed imports for built-ins (`node:fs/promises`, `node:crypto`).
- **Logging pattern**: `client.app.log` no longer exists on v2. Every plugin logs through the host's **Effect logger**: `captureHostContext` runs once *inside the plugin's own Effect* (`yield* captureHostContext`), `createEffectLogger(hostContext, () => logLevel)` adapts it to the package's `Logger` interface (`trace`/`debug`/`info`/`warn`/`error` + fields as log annotations), and records reach OpenCode's own log file — never the terminal ([ADR-0014](docs/adr/0014-suite-wide-no-terminal-mirror.md), mechanism per ADR-0019). Capturing the context anywhere else (a bare `Effect.runFork`) logs to the terminal and fails no type check. `VYMALO_PLUGIN_CONSOLE_LOG=1` is the opt-in console mirror. The level comes from the plugin's own `options.logLevel`, then `OPENCODE_LOG_LEVEL` (`resolveLogLevel`), and is gated a second time by the host's Effect minimum level. Event names use `snake_case` (`models_info_cache_hit`, `oauth2_token_refreshed`). Add new events to that pattern, not ad-hoc `console.log`.
- **`effect` is a `peerDependency` (`^4.0.0`) plus a `devDependency`, never a runtime dependency.** The host supplies the instance (plugin imports of `effect` resolve to the host's own module); a second bundled copy does not share fiber, logger or `Schema` internals and **silently breaks logging**. `@opencode/plugin` is a normal dependency. Keep `effect` external in anything that bundles a plugin. See [ADR-0019](docs/adr/0019-opencode-v2-cutover.md).
- **Cache layout** mirrors per-OS conventions — `~/Library/Caches/<ns>/` on macOS, `XDG_CACHE_HOME` on Linux, `LOCALAPPDATA` on Windows. Each plugin uses its own namespace (`opencode-oauth2`, `opencode-models-info`). Disk writes are atomic-rename + `0o600`.
- **Identifiers we mint are CUID2, never a new UUID call site.** Every id that identifies one of *our own* records — think `browserId` in the browser extension's `settings` table — is a [CUID2](https://github.com/paralleldrive/cuid2) (24 chars, lowercase `a-z0-9`, starts with a letter). Reference implementation for TS: [`@paralleldrive/cuid2`](https://www.npmjs.com/package/@paralleldrive/cuid2). Don't add a new `crypto.randomUUID()` / `uuid` / `nanoid` call site for a record id. Source of truth: [ADR 0039](https://github.com/ADORSYS-GIS/webank-context/blob/master/decisions/0039-cuid2-is-the-house-id-format.md). This bans **minting**, not **storing or accepting** — three carve-outs matter:
  - **OAuth2/OIDC security parameters stay cryptographically random, never CUID2.** `state`, `nonce`, `code_verifier`, and any other CSRF/replay token must keep coming from a CSPRNG (`node:crypto`'s `randomBytes`/`randomUUID`) — see `packages/opencode-oauth2/src/oauth/pkce.ts`. CUID2 is an id scheme optimized for collision-resistance, not a security primitive, and substituting one for a security parameter would be a regression, not a cleanup.
  - **Ids we don't own pass through untouched.** Provider model ids, `sub`, `jti`, `serverId`, and any other id issued by an upstream system are opaque strings — accept them exactly as they arrive, never reshape, regenerate, or shape-validate them (no regex/parse/length check on an id).
  - **Never sort or paginate by id.** CUID2 has no ordering guarantee — use `created_at`/`ts` for that.

## Shell / GitHub gotchas

- **Default shell is zsh** on this laptop. `bash -c` scripts in tooling should stay POSIX-portable or be invoked under zsh explicitly.
- **`gh` auth** lives in the interactive zsh profile. If `gh` looks unauthenticated under a plain non-interactive shell, retry under `zsh -i -c '…'` — `GITHUB_TOKEN` is loaded from `.zshrc`.
- **Biome and the `.claude` worktree path.** `biome.json` excludes `**/.claude`, and Claude Code worktrees live under `.claude/worktrees/<id>/`. A bare `biome … .` therefore self-excludes (the `.` arg resolves under `.claude`) and silently processes **zero** files. To avoid that trap, the root `lint` / `format` / `format:check` scripts pass **explicit paths** (`packages apps test-env *.json`) instead of `.` — Biome evaluates `includes` relative to `biome.json`, so those relative paths never hit the `.claude` exclusion and the scripts work identically from a worktree or the main checkout. If you add a new top-level lintable directory, add it to those three scripts (otherwise it won't be checked). `biome.json` also excludes `**/.output` and `**/.wxt` (WXT's generated build + type output under `apps/browser-extension`).

## Working methodology (how we collaborate here)

The rhythm this repo is built on — follow it unless the user says otherwise:

- **Implement and document together.** A change and its docs land in the same PR — never "code now, docs later". If you touch behavior, update the relevant `docs/`, README, ADR, and `CHANGELOG.md` in the same change. One PR per concern: keep each PR scoped to a single coherent topic rather than bundling unrelated work.
- **Branch → PR → squash-merge.** Work on a branch off `main`, run the pre-push gate (`pnpm -r build && pnpm -r typecheck && pnpm coverage && pnpm lint && pnpm format:check`), then open a PR with `gh`. **Always squash-merge** with `gh pr merge <n> --squash --admin` — never a plain merge commit, never a rebase-merge. One squashed commit per PR keeps `main` linear and the changelog attributable.
- **Merge and publish only when explicitly asked.** Open PRs and push freely, but **do not merge or publish on your own initiative** — wait for the user to say "merge it" / "publish" / "release". When they do say "publish" or "release", that means `gh workflow run publish.yml -f dry_run=false` (see [Releasing](#releasing)) — **never** create a GitHub Release or git tag.
- **One version line, one changelog entry.** All sixteen packages bump together; the bump PR also adds the `CHANGELOG.md` entry for that version. See [Releasing](#releasing) and [Changelog](#changelog).
- **Shell + `gh` under interactive zsh.** `gh` (and push) auth lives in the interactive zsh profile — run them as `zsh -i -c '…'` (see [Shell / GitHub gotchas](#shell--github-gotchas)).

## Releasing

Versions are bumped **manually** — there are no changesets and no release scripts. `@vymalo/opencode-auth-core`, `@vymalo/opencode-core-otel`, `@vymalo/opencode-provider-sync`, `@vymalo/opencode-oauth2`, `@vymalo/opencode-models-info`, `@vymalo/opencode-ratelimit`, `@vymalo/opencode-browser`, `@vymalo/opencode-browser-mcp`, `@vymalo/opencode-devtools`, `@vymalo/opencode-devtools-mcp`, `@vymalo/opencode-otel`, `@vymalo/opencode-repo-auth`, and `@vymalo/opencode-lightbridge` are the **thirteen** published packages; the workspace root, `@vymalo/opencode-oauth2-bundle`, `@vymalo/opencode-browser-extension` (the WXT app) are the **three** `private` packages. `opencode-browser-mcp` depends on `opencode-browser`, and `opencode-devtools-mcp` on `opencode-devtools`, via `workspace:*` (pnpm rewrites them to the real version on publish); `opencode-repo-auth` and `opencode-otel` each depend on one shared core (`opencode-auth-core`, `opencode-core-otel` respectively) the same way; `opencode-oauth2` depends on **both** `opencode-auth-core` and `opencode-provider-sync`; `opencode-lightbridge` depends on **both** shared cores; the bundle depends on oauth2 the same way — so a version bump touches only `package.json` `version` fields (no lockfile change). All sixteen packages (the thirteen published plus the three private) are kept on the **same version line** — currently `0.18.1` — and bumped together in **one PR that also updates [`CHANGELOG.md`](CHANGELOG.md)** (see below).

Publishing runs through the **`publish.yml` workflow**, never a local `npm publish`: trigger it with `gh workflow run publish.yml -f dry_run=false` (off `main`, after the bump PR merges). It builds and publishes the thirteen npm packages at the new version, in dependency order (`auth-core` → `core-otel` → `provider-sync` → everything that depends on any of the three, `oauth2` after `provider-sync`, `lightbridge` last since it depends on both cores). **Do not create a GitHub Release or a git tag** — the repo deliberately has none; releases are driven by the workflow run, not by tags. The **browser-extension** is private (never npm) but is still a release artifact: `publish.yml` runs `wxt zip` (Chrome + Firefox + a Firefox sources zip) and attaches the zips, so the browser feature ships as **three** things — `@vymalo/opencode-browser` (npm), `@vymalo/opencode-browser-mcp` (npm), and the extension zip(s). A separate `submit-extension` job (`needs: publish`) also runs `wxt submit` to push the extension to the **Chrome Web Store** and **Firefox AMO** — each store is gated on its own repo secrets (`CHROME_*` / `FIREFOX_*`) so a store with no credentials is skipped, not failed; a `workflow_dispatch` with `dry_run: true` runs `wxt submit --dry-run` to validate creds without uploading. Store setup + the secret list live in [`docs/browser.md`](docs/browser.md) → "Publishing the extension to the web stores" (local creds go in `apps/browser-extension/.env.submit`, gitignored; template at `.env.submit.example`).

**How the workflow decides what to publish — and when it may skip.** The ordered package list lives in exactly one place, `PUBLISH_ORDER` in [`scripts/release/publish-guard.mjs`](scripts/release/publish-guard.mjs) (the pack, tarball-verify and publish steps all loop over it; a Vitest drift guard fails CI if it stops matching the non-private workspace packages or the dependency order). Two phases, both from that script:

- **Preflight, before anything is installed or pushed** (runs in `dry_run: true` too): classify every package's version on the registry, and for each one that still has to publish run the npm Trusted Publishing OIDC token exchange — the call pnpm makes before its `PUT`, without the `PUT`. A package with no Trusted Publisher, or a name that was never bootstrapped, fails the run here with nothing published, so a release goes out whole or not at all (run `42573812315` instead failed partway, leaving `auth-core`/`core-otel` at the new version and the rest at the old).
- **Publish loop.** A version already on npm is skipped **only if** the registry holds a provenance attestation for it built by this repo's `.github/workflows/publish.yml` (`dist.attestations`, SLSA `buildDefinition.externalParameters.workflow`). A version on npm *without* that proof — a manual publish, another workflow — **fails the run** instead of reporting "already released": the pipeline has never shown it can publish that package. (The old `npm view` skip hid exactly this for `provider-sync` from 0.17.0 to 0.18.0; runs `33864587568`, `42573812315`.) A genuine re-run of a release this workflow already published still skips cleanly.

### Adding a new published package (bootstrap — do this or the pipeline will not publish it)

npm Trusted Publishing cannot create a package name; it can only be attached to one that already exists. So a new published package needs, in order:

1. Add its directory to `PUBLISH_ORDER` (after everything it depends on) (the drift test fails until you do), and keep it on the shared version line.
2. **Publish the first version by hand** to reserve the name (`pnpm --filter <pkg> publish --access public --no-git-checks`, with your own npm credentials; no `--provenance` — it only works inside CI).
3. **Attach a Trusted Publisher on npmjs.com** (package → Settings → Trusted Publisher → GitHub Actions: this repo, workflow `publish.yml`).
4. Only then release. Until step 3 is done the preflight fails for the package's *next* version (OIDC exchange 404), and the hand-published version itself is rejected as "no provenance" if the workflow meets it — by design; before this guard it was silently skipped forever, which is how `provider-sync` went two months unpublishable. Bump the version after attaching the publisher, then release as normal.

### Dist-tags (`dist-tag.yml`)

`.github/workflows/dist-tag.yml` (manual, `dry_run` defaults to `true`) points one dist-tag at one existing version on all thirteen packages, e.g. `gh workflow run dist-tag.yml -f dry_run=false` for the default `opencode-v1` -> `0.17.0`. It never publishes, never touches `latest`, and is idempotent. Things that will bite:

- **Needs a per-package opt-in that CI cannot create.** npm Trusted Publishing authorizes dist-tag writes only when the trusted publisher config has **"Allow npm dist-tag"** enabled (off by default, independent of publish permission). npm matches the OIDC token to a config by **workflow filename**, so each of the thirteen packages needs a *second* Trusted Publisher config for `dist-tag.yml` (package -> Settings -> Trusted Publisher) with that option on; the `publish.yml` config does not cover it. Same shape as the bootstrap below: an invisible per-package npm setting. The workflow's plan phase fails on a missing config (OIDC exchange 404) with nothing changed; a missing "Allow npm dist-tag" can only be detected by the write, so `apply` reports all failing packages at once and a re-run is safe.
- **npm >= 11.21.0 (or >= 12.2.0), not the Node-bundled npm.** The job installs `npm@^11` (not `@latest`); it uses `npm dist-tag`, the documented OIDC path, not `pnpm`.
- **A tag cannot be called `v1`.** npm rejects any dist-tag that is a valid SemVer range, and `v1` is one. The v1 install target is `opencode-v1`.

### Changelog

Every release is recorded in [`CHANGELOG.md`](CHANGELOG.md) — [Keep a Changelog](https://keepachangelog.com/) format, SemVer. All sixteen packages are kept on the same version line, there is a **single consolidated entry per version** (not per-package files); tag each line with the package it touches (`auth-core`, `core-otel`, `provider-sync`, `oauth2`, `models-info`, `ratelimit`, `browser`, `browser-mcp`, `browser-extension`, `oauth2-bundle`, `devtools`, `devtools-mcp`, `otel`, `repo-auth`, `lightbridge`) and link the PR. Group changes under `Added` / `Changed` / `Fixed` / `Documentation`. **Update the changelog in the same PR as the version bump** — the bump and its notes land together. Entries are attributed by `chore(release)` bump-commit boundaries (there are no git tags to anchor them).
